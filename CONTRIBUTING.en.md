# Contributing

[中文](CONTRIBUTING.md) | **English**

This project uses a **strict PR workflow**: `main` is protected, and every change must land via a
branch plus a pull request.

## 1. Setup

| Dependency | Version | Notes |
|---|---|---|
| Rust | 1.99.1 | Pinned by `rust-toolchain.toml`; `rustup` installs it on the first `cargo` call |
| Node.js | ≥ 22 | Frontend and Tauri CLI |
| pnpm | ≥ 10 | Package manager; do not mix in npm/yarn lockfiles |

Windows needs MSVC Build Tools. Linux needs `libwebkit2gtk-4.1-dev`, `libappindicator3-dev`,
`librsvg2-dev` and `patchelf`.

## 2. Pre-submit checks

Before opening a PR, these must pass locally (identical to CI):

```bash
cargo fmt --all --check
cargo clippy --workspace --all-targets -- -D warnings
cargo test --workspace --all-features
cargo deny check licenses bans sources

pnpm lint
pnpm test
pnpm build
```

`cargo deny`'s `advisories` check clones the RustSec database. If your network blocks it, running
`licenses bans sources` alone is acceptable locally — CI runs the full set.

## 3. Branch naming

| Prefix | Purpose | Example |
|---|---|---|
| `feat/` | New feature | `feat/core-rules-eval` |
| `fix/` | Bug fix | `fix/java-path-with-spaces` |
| `refactor/` | Behaviour-preserving refactor | `refactor/downloader-split` |
| `docs/` | Documentation | `docs/development-plan` |
| `ci/` | CI / build | `ci/pr-gates` |
| `chore/` | Dependencies, config, scaffolding | `chore/repo-bootstrap` |

Aim for a branch lifetime of ≤ 3 days. Split large features into **stacked PRs** and state the
dependency order and target branches in the description.

## 4. Commit messages

Follow [Conventional Commits](https://www.conventionalcommits.org/):

```
<type>(<scope>): <subject>
```

Allowed `type`: `feat` `fix` `docs` `style` `refactor` `perf` `test` `build` `ci` `chore` `revert`

Common `scope`: `core` `net` `auth` `java` `app` `ui` `loader` `mods` `update` `release` `ci` `deps`

PR titles must follow this format: merges are squashed, so **the PR title becomes the commit
message** and ends up verbatim in the changelog.

## 5. Hard rules for PRs

1. **One PR, one concern.** Never mix a feature with a refactor.
2. **Effective diff ≤ 400 lines** (excluding tests, generated code and lockfiles). Anything larger
   must be split. Infrastructure PRs (templates, config, docs) are exempt but must explain their
   composition in the description.
3. **Tests required**: new logic needs unit tests; bug fixes need a regression test that fails
   without the fix.
4. **Docs required**: changes to architecture, IPC contracts or config formats must update `docs/`;
   significant technical decisions need an ADR in `docs/adr/`.
5. **Never commit**: commented-out code, `dbg!`/`println!` debugging, secrets or absolute local
   paths, unused dependencies.
6. **Green CI plus a completed PR checklist** before requesting review.

## 6. Review and merge

- At least 1 approval, and all review comments resolved.
- Branch must be up to date with `main`.
- **Squash and merge**; the branch is deleted automatically afterwards.
- Force pushing to protected branches is forbidden.

## 7. Code style

- Rust formatting is defined by `rustfmt.toml`; no formatting debates.
- `clippy -D warnings` is treated as an error. Genuine exceptions need a local `#[allow(...)]` with a
  written reason.
- Error types: `thiserror` for classified errors in library crates, `anyhow` for context in the app
  layer.
- Public APIs must be documented (`missing_docs` is a warning, which CI promotes to an error).
- Frontend linting uses **oxlint** (`pnpm lint`), configured in `.oxlintrc.json`. Do not add eslint:
  `typescript-eslint`'s peer dependency does not support the TS 7 this project uses.
- Keep pure logic in `src/lib/`; components should only render. Pure-function tests run in
  milliseconds and need no DOM.
- If a test touches platform differences (path shapes, shell semantics, `#[cfg]` imports), ask
  "does this line still hold on the other platform?" — passing locally does not mean passing in CI.

### Preview page for UI work

`LauncherView` is a pure presentational component. Run `pnpm dev` and open
<http://localhost:5173/preview.html> to render the full interface with mock data — no desktop shell,
no real version download.

Check visual changes there first, and keep the mock data in `src/preview.tsx` up to date.

## 8. Changelog

`CHANGELOG.md` is generated by [git-cliff](https://github.com/orhun/git-cliff) from Conventional
Commits and is **never edited by hand**.

```bash
git cliff --config cliff.toml -o CHANGELOG.md    # regenerate everything
git cliff --config cliff.toml --unreleased       # preview the unreleased section
```

It is generated **before a release**, not per PR. The unreleased section is "every commit since the
last tag", so regenerating it in each PR guarantees conflicts between parallel PRs and constant
reordering.

Corollary: **PR titles appear verbatim in the changelog**. That is the practical reason Section 4
insists on Conventional Commits — it decides whether users read
"feat(core): domain model for version manifest and metadata" or "update stuff".

## 10. Chinese name database

Modrinth's search index is English-only (Chinese queries return 0 hits), so Chinese names come from
a local database: `assets/data/mod-zh.json`, keyed by project **slug**.

```json
{
  "sodium": "钠",
  "create": "机械动力"
}
```

To add an entry:

1. Confirm the slug matches the project at `https://modrinth.com/mod/<slug>`
2. Add one line to the JSON (**one entry per line**, for review and merges)
3. Run `cargo test -p qcl-mods` — it validates the JSON, rejects empty values and **duplicate keys**

Conventions:

- Translate **names only**, not descriptions. Descriptions are long and terminology-heavy; machine
  translation is unreliable there, so the UI links to the Modrinth page instead.
- Proper nouns may stay in English (e.g. `Fabric API`, `Jade`).
- Use a middle dot for qualifiers: `"iris": "铱 · 光影加载器"`.
- The database ships with the binary and is not fetched at runtime, so changes take effect in the
  next release.

## 11. Releases

Releasing is the maintainer's job, but changes can break the release pipeline, so the rules live here:

- **The version lives in three places**: `package.json`, `src-tauri/tauri.conf.json` and
  `[workspace.package]` in `Cargo.toml`. All three must match; the release workflow verifies this and
  fails otherwise.
- **Do not bump the version in a normal PR** unless that PR is the release preparation itself.
  Version bumps in unrelated branches only create conflicts.
- If you touch `src-tauri/tauri.conf.json`, `src-tauri/capabilities/`, `.github/workflows/release.yml`
  or `scripts/`, read [docs/RELEASE.en.md](docs/RELEASE.en.md) first — mistakes there only surface
  during a release.

Full release process, signing key management and troubleshooting:
[docs/RELEASE.en.md](docs/RELEASE.en.md) ([中文](docs/RELEASE.md)).
