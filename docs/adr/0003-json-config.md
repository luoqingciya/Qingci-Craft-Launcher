# ADR-0003：配置用 JSON 而非 SQLite

- 状态：已接受
- 日期：2026-10-24（本 ADR 补记于 2026-10-28，决策在项目初始就已确定并落地）
- 决策者：@luoqingciya

## 背景

需要持久化的东西很少：游戏目录、离线玩家名、最大内存、Java 路径、下载源、以及实例列表（名字 + 目录 + 当前选中的版本）。
量级是「十几个字段」，写入频率是「用户点保存时」，读取频率是「启动时一次」。

可选方案有三类：单文件（JSON / TOML）、嵌入式数据库（SQLite）、系统注册表或 GSettings 之类的平台机制。

## 决策

用一个 `settings.json`，结构由 `serde` 定义，放在应用配置目录（便携版放在 exe 旁边）。

## 理由

1. **没有并发写者**：启动器有单实例锁，同一时间只有一个进程在写，不需要事务或行锁。
2. **可读、可改、可贴**：出问题时让用户把文件内容贴出来就能定位，自己改一个值也不必装工具。排障成本远低于「请用 sqlite3 打开这个文件」。
3. **演进不需要迁移机制**：字段用 `#[serde(default)]`，旧文件缺字段就用默认值，多出来的字段被忽略。加一个设置项不必写 migration。
4. **与「便携」这个卖点一致**：整个目录拷走就完成迁移。SQLite 文件同样能拷，但会引入 native 依赖（Windows 上要打包 DLL、交叉编译时更要小心），而收益只是「万一将来数据变大」。
5. **体积**：省一个 native 库，对 12 MB 的目标体积是实打实的。

## 后果

- **没有原子写**。`settings::save` 是「序列化 → `fs::write`」，写到一半断电或磁盘满，会留下一个坏文件；而 `settings::load` 在解析失败时**静默退回默认值**——用户会看到设置全没了，且不知道原因。
  这是当前的真实短板。改进方向是「写临时文件 + rename」，属于独立改动，不在本 ADR 的范围内。
- **没有查询能力**：将来若要做「历史记录」「统计」这类需要按条件检索的数据，JSON 会不合适。届时应另开一个存储（SQLite 或别的），而不是把 `settings.json` 撑大。
- **文件是明文**：所以令牌绝不进这个文件（见 [SECURITY.md](../../SECURITY.md) 的「令牌只进系统凭据库」）。

## 替代方案

- **SQLite（`rusqlite` / `sqlx`）**：为十几个字段引入 schema、迁移与 native 依赖，收益在当前规模下为零。
- **TOML**：同样合适，但前端与 Rust 两侧都要序列化设置，JSON 是两者共同的原生格式，少一层转换。
- **平台机制（注册表 / GSettings）**：与「便携版把目录拷走就迁移」直接冲突，且要写三套平台代码。
