# ADR-0004：认证采用设备码流程

- 状态：已接受
- 日期：2026-10-24（本 ADR 补记于 2026-10-28，实现见 `qcl-auth`）
- 决策者：@luoqingciya

## 背景

要让用户用自己的微软账号启动正版。可选的 OAuth 2.0 授权方式有三种：

1. **授权码 + 本地回调**（`http://localhost:PORT` 起一个临时服务接 redirect）
2. **授权码 + 内嵌浏览器 / WebView 窗口**
3. **设备码流程**（`urn:ietf:params:oauth:grant-type:device_code`）

## 决策

采用**设备码流程**：向 `https://login.microsoftonline.com/consumers/oauth2/v2.0/devicecode` 请求一个
用户码，界面显示「去 `microsoft.com/link` 输入 XXXX-XXXX」，用户在**自己的浏览器**里完成登录，
启动器按 `interval` 轮询 `/token` 直到拿到令牌。

客户端 ID 在编译期由 `QCL_MS_CLIENT_ID` 注入，不进仓库——它是发布者自己的 Azure 应用注册。

## 理由

1. **碰不到密码**：密码只输入在微软自己的页面里。启动器全程不渲染任何凭据输入框，也就不存在「仿冒登录框」这一类问题。
2. **不需要本地监听端口**：方案 1 要在本机起 HTTP 服务接回调。启动器是桌面程序，开端口会被防火墙询问、可能与占用冲突，还要处理「谁先点了链接」的竞态。
3. **不需要内嵌浏览器**：方案 2 要把 WebView 变成浏览器，得处理第三方 Cookie、User-Agent、以及用户对「为什么启动器里有个浏览器」的疑虑。
4. **令牌由系统凭据库保管**：持久化的只有微软的刷新令牌（Minecraft 访问令牌活不过一小时），写进 Windows Credential Manager / macOS Keychain / Linux Secret Service，**不写配置文件**。
5. **不需要 PKCE 与 `state`**：这两个机制解决的都是「重定向环节」的问题——授权码在跳转途中被截获、CSRF 靠 `state` 回传来证明请求出自本人。设备码流程**没有重定向、没有授权码**，这两个机制无处落脚。详细对照见 [SECURITY.md](../../SECURITY.md) 的「登录流程的信任边界」。

## 后果

- **多一步操作**：用户要手动打开浏览器并输入 8 位码。这是设备码流程的固有代价，换取的是上面几条。
- **依赖浏览器**：完全没有浏览器的环境（极少见）无法登录。此时仍可用离线账户启动，功能不受影响，只是不能进正版服务器。
- **轮询要守规矩**：必须按服务端给的 `interval` 轮询，收到 `slow_down` 要退避，否则会被限流。这些在 `qcl-auth` 里有对应处理。
- **应用注册是发布者的责任**：公共客户端没有 client secret（ID 在请求表单里明文出现，抓包可见），所以它不是机密；但应用注册本身要维护，且 Mojang 侧需要相应的审核。

## 替代方案

- **授权码 + 本地回调**：体验最顺（点一下，浏览器回来就好了），但要在本机开端口并处理回调竞态，与「轻量、无副作用」的取向冲突。
- **内嵌浏览器**：把复杂度从「开端口」转移到「维护一个浏览器」，且用户难以判断页面真伪。
- **第三方认证服务（如 littleskin 之外的聚合登录）**：把账号安全交给第三方，与本项目的信任模型不符。
